# Testpilot для 1С у Codex

Використовуй цей скіл для керування тестовим клієнтом 1С через MCP `1c-testpilot`. Клієнт працює з `/TESTCLIENT` і приймає підключення на TCP-порту. Дії виконуються в межах погодженого сценарію та тестової бази.

## Середовище та документація

- Проєктні вимоги: Локально 2026-10-05 перевірено наявність `C:\Program Files\BAF\8.3.23.2299\bin\1cv8.exe` та пакета Testpilot 1.7.1 у pipx. Версію фактично запущеного клієнта визначай перед підключенням.
- Локальний виконуваний файл сервера: `C:\Users\Server\.local\bin\1c-testpilot.exe`. Налаштування MCP змінюй лише в межах окремого запиту на налаштування.
- Стан з’єднань і профілів визначай щоразу через `list_connections` та `list_profiles`. Порт, `connection_id`, наявність профілю та активне вікно не є постійними властивостями скіла.
- Інструменти можуть мати префікс `mcp__1c_testpilot__`; використовуй фактичні назви й описи дій, доступні в поточній сесії Codex. Для звичайного сценарію достатньо груп `tc_session`, `tc_find`, `tc_window`, `tc_field`, `tc_table`; `tc_form` потрібен для контексту й знімків.
- Точні сигнатури перевіряй у текстових описах конкретних дій або в документації встановленої версії. Загальна схема групи допускає параметри, які може не приймати окрема дія. Документація гілки `main` може описувати новішу версію сервера.

## Підключення та готовність

1. Виклич `tc_session(action="list_connections")`. Це реєстр з’єднань цього MCP-сервера, а не перелік усіх запущених клієнтів 1С. Порожня відповідь не означає, що 1С не запущена.
2. Якщо потрібне з’єднання зареєстроване, врахуй `connected`, `busy`, `active_action` та `launched`. При кількох з’єднаннях визнач цільову базу й користувача та передавай відповідний `connection_id`. Не переривай зайняте з’єднання автоматично.
3. До вже запущеного клієнта під’єднуйся через `connect` з перевіреними `host`, `port` і точною `version` або через профіль підключення з `list_profiles`. Профіль запуску з параметром `base` не слід вважати профілем підключення. Порт і версію отримай із параметрів клієнта, перевіреного профілю або даних користувача; не підставляй порт зі старого прогона.
4. Для запуску нового клієнта використовуй `launch_client` із перевіреним профілем або наданими параметрами тестової бази. Профілі необов’язкові для прямого підключення. Якщо потрібних параметрів немає, попроси лише відсутню інформацію; не вигадуй базу чи облікові дані.
5. `connected: true` підтверджує з’єднання, але не готовність UI. Для керованого інтерфейсу дочекайся `tc_find(action="wait_for_object_displayed", cls="ManagedForm")`, потім перевір активне вікно. Для звичайних форм застосовуй перевірку відповідно до фактично доступних класів і можливостей інструментів. При таймауті зафіксуй результат; не запускай дубль клієнта і не вважай сценарій успішним.
6. Навігацію виконуй через `tc_window(action="execute_command", command="e1cib/...")`. Команду визначай за метаданими потрібної конфігурації; звіряй отриману форму з очікуваною. Для пошуку коду й метаданих проєкту користуйся RLM відповідно до інструкцій проєкту.

## Дії та читання результату

- Отримуй `ref` через `tc_find` і передавай його без змін. Після переходу до іншої форми або перепідключення знайди елементи знову.
- Для таблиці знайди рядок, перейди на нього, потім виконай дію над поточним рядком. `find_rows` не переміщує курсор. Враховуй напрямок `goto_row`; для пошуку вище курсора або поза видимою частиною використовуй відповідний напрямок чи перехід до першого рядка.
- Для `set_fields` передавай `entries` з `ref` полів, а не форми. Пакетні дії можуть зупинитися після часткового виконання: прочитай результат і виправ причину перед продовженням.
- Порожні `read_rows`/`find_rows` не доводять відсутність ієрархічного вузла. Перевіряй навігацію через `goto_row` і `choose_row`. Не читай таблиці неактивних вкладок; вибирай потрібну таблицю за її фактичним ім’ям.
- Неочікуване вікно досліди через форму й повідомлення. `answer_dialog` відповідає на стандартне Так/Ні; для інших кнопок знайди потрібну кнопку. Для прикладної помилки прочитай `tc_app(action="get_current_error")` і `details`.
- `ok: true` означає прийняття команди. Для перевірки значення використовуй `value_after`, `verified` та фактичний стан; еквівалентне числове форматування не вважай розбіжністю. Якщо відповідь неповна або перевірка невизначена, перечитай потрібний стан.
- Натискання «Записати» або «Провести» може завершитися до завершення операції 1С. Обмеженим очікуванням перевір завершення, номер/посилання документа та очікуваний статус. Сам номер документа не підтверджує проведення; за потреби перевір рухи незалежним читанням. Після таймауту з невідомим результатом спочатку перевір стан, а не повторюй створення чи проведення.
- Перед дією, для якої перевіряються повідомлення, очисть панель старих повідомлень, якщо це відповідає сценарію; потім прочитай нові. Скриншоти використовуй як додатковий доказ і враховуй `capture_complete`.

## Можливості перевірки даних

Перед плануванням звірки даних перевір наявність `tc_execute_query`, `tc_execute_code`, `tc_get_metadata` та інструментів користувацьких BSL-функцій. Їх публікація залежить від параметрів MCP-сервера та обробки Testpilot; вони не гарантовані кожною сесією.

Якщо потрібного інструмента немає, використай доступний спосіб читання, погоджений для сценарію, або познач звірку даних «не перевірено». UI-доказ і перевірка рухів є окремими результатами. Налаштування `code_epf` і публікації додаткових інструментів виконується в межах запиту на налаштування, а не автоматично під час прогона.

Запити використовуй для читання й підтвердження даних; зміни через BSL або UI мають відповідати погодженому сценарію. Типізовані параметри й обмеження виконання коду перевіряй у документації обробки встановленої версії.

## Докази та завершення

- На початку прогона визнач очікувані результати та доступні перевірки. Для тестових об’єктів використовуй префікс `TESTPILOT`, коли це відповідає сценарію; записуй створені об’єкти та їхні номери/посилання в артефакти прогона.
- Якщо журналювання доступне, перевір `get_logging_status`. Для нового прогона почни власний журнал через `start_logging`; уже активний журнал іншого прогона не заверши. Зберігай кроки й ключові відповіді одразу у папці артефактів прогона. Наприкінці власного журналу виклич `stop_logging` і додай повернуті шляхи до звіту; якщо журнал недоступний, веди файловий протокол.
- Для кожного кроку вкажи очікуваний і фактичний результат, доказ та статус: «пройдено», «не пройдено», «не перевірено». При блокуючому збої збережи дослівну діагностику, познач невиконані залежні кроки «не перевірено» та продовжуй лише незалежні перевірки, які ще мають сенс.
- Перед закриттям зміненої форми прочитай запитання про збереження та дай відповідь відповідно до сценарію. Не завершуй клієнт, щоб приховати незакритий діалог.
- Клієнт, запущений поза Testpilot, залиш відкритим; від’єднуйся лише коли це потрібно для завершення роботи. Власний клієнт, запущений через `launch_client`, завершуй через `stop_client`, якщо сценарій не передбачає наступного раунду або спостереження користувача. Не трактуй примусове завершення як доказ успішного завершення сценарію.
- У режимі спостереження використовуй звичайний робочий стіл, доведи форму до потрібного стану й залиш її відкритою. Після ручних дій користувача перечитай актуальний контекст.

## Контекст та повторювані прогони

- `tc_form.get_context` використовуй для початкового огляду потрібної форми; надалі шукай точково через `tc_find`. Для порівняння стану використовуй знімки й `compare_snapshot`, коли доступні. `tc_form` адресуй актуальним `ref` форми відповідного класу.
- Заповнюй поля через `set_fields`, рядки через `add_rows`, якщо порядок значень узгоджений із залежностями форми. Повторне читання всього дерева замінюй читанням потрібних полів і змін.
- Для перетворення перевіреного сценарію на регулярний прогін прочитай [інструкції Python API та pytest](references/repeatable-runs.md). Це окрема робота за запитом користувача.
