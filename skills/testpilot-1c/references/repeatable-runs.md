# Повторювані прогони через Python API

Читай цей файл, коли користувач просить автоматизувати вже перевірений сценарій або створити регресійні тести.

1. Збережи сценарій, передумови, очікувані результати та докази успішного UI-прогона. Тест має перевіряти ці результати, а не лише факт прийняття команд.
2. Звір API з [PYTHON_TESTING.md](https://github.com/ROCTUP/1c-testpilot/blob/main/docs/PYTHON_TESTING.md) для встановленої версії. Python API працює напряму з клієнтом `/TESTCLIENT`; MCP-сервер для такого скрипта не потрібен.
3. Для кількох незалежних тестів із власними перевірками використовуй pytest та інтеграцію Testpilot. Перевір наявність залежностей у вибраному Python-середовищі; не припускай, що pytest є у pipx-середовищі сервера. Для одного обходу форм можна використати скрипт з одним клієнтом.
4. Якщо використовуються профілі, задай `TC1C_PROFILES_FILE` до запуску Python/pytest. Вибери профіль відповідного призначення. Окремим одночасним клієнтам призначай різні вільні порти або використовуй автоматичне виділення; не займай порт клієнта користувача.
5. Для незалежної перевірки даних звір налаштування `code_epf` із [документацією обробки](https://github.com/ROCTUP/1c-testpilot/blob/main/onec/Testpilot/README.md). Виділи відповідний профіль, коли обробка змінює початковий стан UI. Не вважай доступність функції в Python API доказом її публікації через MCP.
6. Операції запису й проведення перевіряй після завершення. Очікування має мати кінцевий строк і зберігати діагностику при невдачі. Після невизначеного результату прочитай стан перед повторною дією.
7. Зберігай журнал і перелік тестових даних. Завершуй власні клієнти та власне журналювання; видалення бізнес-даних має відповідати погодженому очищенню тестового сценарію.

Передумови й оцінювання складного сценарію можна звірити з [методикою набору](../../../vendor/1c-testpilot-agent-kit/benchmark/METHOD.md); дані його бенчмарку потрібно адаптувати до цільової конфігурації.
